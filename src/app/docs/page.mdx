# Uptime Monitor Documentation

Welcome to the Uptime Monitor documentation. This service provides comprehensive monitoring for your websites and applications with real-time alerts and detailed status tracking.

## Overview

Uptime Monitor is a modern, full-stack monitoring service that helps you keep track of your website and application health. It supports two types of monitoring:

- **HTTP Ping Monitoring**: Scheduled checks that ping your endpoints at regular intervals
- **Application Log Monitoring**: Real-time log ingestion with configurable alert thresholds

## Features

- **Background job processing** with Inngest for reliability
- **Database optimization** with proper indexing and relationships

## Monitor Types

### HTTP Ping Monitors

HTTP Ping monitors perform scheduled HEAD requests to your endpoints at configurable intervals.

**Configuration:**

- **URL**: The endpoint to monitor (must be http:// or https://)
- **Interval**: Check frequency in seconds (default: 300 seconds / 5 minutes)
- **Status**: Active or paused

**How it works:**

1. The system schedules checks based on the `intervalSec` setting
2. A HEAD request is sent to the configured URL
3. Response status and latency are recorded
4. If the endpoint is down, alerts are triggered

**Supported intervals:**

- 1 minute (60 seconds)
- 5 minutes (300 seconds) - Default
- 15 minutes (900 seconds)
- 30 minutes (1800 seconds)
- 1 hour (3600 seconds)

### Application Log Monitors

Application Log monitors receive logs directly from your applications and trigger alerts based on log severity thresholds.

**Configuration:**

- **Service Name**: A unique identifier for your service
- **Alert Threshold**: Minimum log level that triggers alerts
  - `error`: Only error-level logs trigger alerts
  - `warn`: Warning and error logs trigger alerts
  - `info`: Info, warning, and error logs trigger alerts
  - `debug`: All logs trigger alerts

**How it works:**

1. Your application sends logs to the ingestion endpoint
2. Logs are filtered based on the configured threshold
3. Alerts are triggered when logs meet or exceed the threshold
4. No scheduled pings are performed for APP_LOG monitors

**Log Levels (in order of severity):**

- `debug` (lowest)
- `info`
- `warn`
- `error` (highest)

## Alerting System

### Alert Channels

#### Email Alerts

Email alerts are sent via Resend when a monitor goes down. The email includes:

- Monitor name
- URL or service name
- Status details
- Response time (for HTTP_PING monitors)

#### Slack Alerts

Slack alerts use webhook URLs and support rich formatting. Configure your Slack webhook:

1. Go to Settings page
2. Add your Slack webhook URL
3. Test the connection

**Per-monitor Slack webhooks:**

- Each monitor can have its own Slack webhook
- If not configured, falls back to user default webhook
- Configure via the Alert Settings modal on each monitor card

#### Custom Webhooks

Custom webhooks allow integration with any third-party service. The webhook payload includes:

```json
{
  "event": "monitor.down",
  "monitor": {
    "id": "monitor-id",
    "name": "Monitor Name",
    "url": "https://example.com",
    "status": "DOWN",
    "responseTime": 5000
  },
  "timestamp": "2024-01-01T00:00:00.000Z",
  "user": {
    "id": "user-id",
    "email": "user@example.com"
  }
}
```

**Webhook retry logic:**

- 3 attempts with exponential backoff
- Delays: 1s, 2s, 4s
- Returns error if all attempts fail

### Alert Configuration

#### User-level Defaults

Set default webhooks in the Settings page:

- Default Slack webhook
- Default custom webhook

These are used as fallbacks when monitors don't have their own webhooks configured.

#### Per-monitor Overrides

Each monitor can have its own alert configuration:

- Monitor-specific Slack webhook
- Monitor-specific custom webhook

**Priority order:**

1. Monitor-specific webhook (if configured)
2. User default webhook (if configured)
3. No alert sent (if neither is configured)

## Getting Started

### Prerequisites

- Node.js 18+
- PostgreSQL database
- Google OAuth credentials
- Resend API key (for email alerts)
- Inngest account (for background jobs)

### Installation

1. **Clone the repository**

   ```bash
   git clone <repository-url>
   cd uptime-service
   ```

2. **Install dependencies**

   ```bash
   npm install
   ```

3. **Set up environment variables**
   Create a `.env.local` file:

   ```env
   # Database
   DATABASE_URL="postgresql://username:password@localhost:5432/uptime_monitor"
   DIRECT_URL="postgresql://username:password@localhost:5432/uptime_monitor"

   # Authentication
   BETTER_AUTH_SECRET="your-secret-key"
   BETTER_AUTH_URL="http://localhost:3000"

   # Google OAuth
   GOOGLE_CLIENT_ID="your-google-client-id"
   GOOGLE_CLIENT_SECRET="your-google-client-secret"

   # Email (Resend)
   RESEND_API_KEY="your-resend-api-key"

   # Inngest
   INNGEST_EVENT_KEY="your-inngest-event-key"
   INNGEST_SIGNING_KEY="your-inngest-signing-key"
   ```

4. **Set up the database**

   ```bash
   npx prisma generate
   npx prisma db push
   ```

5. **Start the development server**

   ```bash
   npm run dev
   ```

6. **Open your browser**
   Navigate to [http://localhost:3000](http://localhost:3000)

## Usage Guide

### Creating a Monitor

1. **Sign in** with Google OAuth
2. **Click "Add Monitor"** on the dashboard
3. **Select monitor type**:
   - HTTP Ping: For website/API monitoring
   - Application Logger: For log-based monitoring
4. **Configure monitor settings**:
   - **HTTP Ping**: Enter URL and interval
   - **Application Logger**: Enter service name and alert threshold
5. **Set active status** (enabled by default)
6. **Save** the monitor

### Configuring Alerts

#### Global Settings

1. Go to **Settings** page
2. Add your **Slack webhook URL** for Slack notifications
3. Add your **custom webhook URL** for third-party integrations
4. Test your webhook configuration

#### Per-monitor Settings

1. Click the **bell icon** on any monitor card
2. Toggle **Slack alerts** and enter webhook URL (optional)
3. Toggle **Custom webhook** and enter webhook URL (optional)
4. Click **Test Webhook** to verify configuration
5. Save settings

### Managing Monitors

- **Edit**: Click the edit icon on a monitor card
- **Pause/Resume**: Toggle the active switch in the edit modal
- **Delete**: Click the delete icon (with confirmation)
- **Search**: Use the search bar to filter monitors by name

### Monitoring Behavior

**HTTP Ping Monitors:**

- Checks run automatically based on `intervalSec`
- Only active monitors are checked
- Next check time is calculated automatically
- Status updates in real-time

**Application Log Monitors:**

- No scheduled checks
- Alerts triggered when logs are received
- Logs must meet or exceed the configured threshold

### Tech Stack

**Frontend:**

**Backend:**

- Server Actions for API operations

**External Services:**

- Resend for email delivery
- Google OAuth for authentication
- Slack Webhooks for notifications

### Background Jobs

The system uses Inngest for reliable background job processing:

1. **Schedule Checks** (runs every minute)
   - Finds monitors due for checking
   - Only processes HTTP_PING monitors
   - Triggers check events

2. **Check Monitor** (triggered by schedule)
   - Performs HEAD request
   - Records status and latency
   - Schedules next check
   - Triggers alerts if down

3. **Send Alert** (triggered on monitor down)
   - Sends email via Resend
   - Sends Slack alert (if configured)
   - Sends custom webhook (if configured)
   - Prevents duplicate alerts (30-minute cooldown)

### Database Schema

**User Model:**

- User information and authentication
- Default webhook configurations
- One-to-many relationship with monitors

**Monitor Model:**

- Monitor configuration and status
- Per-monitor webhook settings
- Type-specific fields (serviceName, logThreshold for APP_LOG)

**Session & Account Models:**

- Better Auth session management
- OAuth account linking

## API Reference

### Server Actions

#### Monitor Actions

- `createMonitor(monitor: CreateMonitorInput)`: Create a new monitor
- `updateMonitor(monitor: UpdateMonitorInput)`: Update an existing monitor
- `deleteMonitor(id: string)`: Delete a monitor
- `getMonitors(search?: string)`: Get all monitors for the current user

#### Alert Actions

- `updateMonitorAlerts(monitorId, alerts)`: Update per-monitor alert settings
- `getMonitorAlerts(monitorId)`: Get alert settings for a monitor
- `sendTestWebhookForMonitor(monitorId)`: Test webhook configuration

### API Routes

- `POST /api/test-webhook-monitor`: Test monitor webhook
- `POST /api/inngest`: Inngest webhook endpoint
- `GET/POST /api/auth/[...all]`: Better Auth endpoints

## Best Practices

### Monitor Configuration

1. **Set appropriate intervals**: Balance between responsiveness and server load
2. **Use descriptive names**: Make it easy to identify monitors
3. **Configure alerts**: Set up webhooks for critical monitors
4. **Test webhooks**: Use the test button to verify configuration

### Alert Management

1. **Use per-monitor webhooks** for different teams/services
2. **Set user defaults** for common alert destinations
3. **Monitor alert delivery**: Check that alerts are being received
4. **Avoid alert fatigue**: Use appropriate log thresholds

### Performance

1. **Limit monitor count**: Too many monitors can impact performance
2. **Use appropriate intervals**: Don't check too frequently
3. **Monitor database size**: Clean up old status history if needed

## Troubleshooting

### Monitors not checking

- Verify monitor is active
- Check that monitor type is HTTP_PING (APP_LOG monitors don't have scheduled checks)
- Ensure Inngest is properly configured
- Check database connection

### Alerts not sending

- Verify webhook URLs are correct
- Test webhook configuration
- Check that monitor/user has webhook configured
- Review alert cooldown (30 minutes between duplicate alerts)

### Authentication issues

- Verify Google OAuth credentials
- Check BETTER_AUTH_SECRET is set
- Ensure BETTER_AUTH_URL matches your domain
